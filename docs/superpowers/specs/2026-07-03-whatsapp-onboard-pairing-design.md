# WhatsApp Onboard Live-Pairing Step — Design

Status: approved by user, ready for implementation plan.

## Context

`brai onboard channels` already lets an operator configure WhatsApp Web:
`Section::Channels`'s `prompt_fields_under` is schema-driven (reflects on
`WhatsAppConfig`'s fields via `Config::prop_fields()`), so it already prompts
for `session_path`, `pair_phone`, `master_identity`, `contact_gate_enabled`,
etc. without any WhatsApp-specific code — this was a side effect of adding
those fields to the schema in the contact-gate branch.

What's missing: after the wizard writes the config, nothing actually
connects to WhatsApp. The pair-code needed to link the dedicated second
number is generated by the WhatsApp server only once `WhatsAppWebChannel::
listen()` runs, and today that code is only visible via `eprintln!`/
`tracing` in the running `brai` service's logs (`journalctl -u brai -f`).
That's the "too hard" gap this design closes: after onboarding, the user
should see the pair-code and a "connected" confirmation right there in the
terminal, without needing to know about journalctl or the systemd service
at all for this one step.

## Architectural constraint discovered during design

`zeroclaw-runtime` (which owns `onboard/mod.rs`) is a dependency *of*
`zeroclaw-channels` (which owns `WhatsAppWebChannel`), not the other way
around — `zeroclaw-channels/Cargo.toml` has `brai-runtime.workspace = true`.
This means `onboard/mod.rs` cannot import `WhatsAppWebChannel` directly
without creating a circular crate dependency.

Only the top-level `brai` binary (`src/main.rs`) depends on both crates.
Consequently, the live-pairing step cannot run *inside* the generic
`channels()` onboard section, immediately after the WhatsApp fields are
filled in. Instead, it runs in `main.rs`, triggered right after `run_onboard(...)`
returns (the wizard's normal exit point), once per invocation, only when
WhatsApp was actually newly configured. The onboard wizard itself
(`onboard/mod.rs`) is **not modified** — it stays fully generic, exactly as
it is today for every channel including WhatsApp.

## Decisions (from brainstorming)

- Live-pairing step triggers automatically after the onboard wizard exits
  (not mid-wizard, per the architectural constraint above), only if the
  WhatsApp config section was newly created or its `pair_phone`/
  `session_path` changed during this run.
- Success detection is **automatic**: the step waits for wa-rs's
  `Event::Connected`, not a manual "did you link it? y/n" prompt.
- Timeout: **60 seconds** per phase (waiting for the pair-code to appear;
  separately, waiting for `Connected` after the code is shown) — matches
  WhatsApp's own pair-code expiry window.
- `master_identity` gets **basic validation + normalization** before being
  saved: strip non-digit characters (keep only digits, ignore any leading
  `+` the user typed) and store as `+<digits>`, consistent with the
  normalization fix already applied to `gate_decision` in the contact-gate
  work. Reject empty results and re-prompt.
- On success: print a clear "restart the brai service now" instruction.
  **No automatic service restart** — this is a `systemctl`/deployment-specific
  action outside brai's control, and matches the project's default posture
  of not taking system-level actions without explicit operator action per
  invocation.
- On failure (`LoggedOut`, `StreamError`, or timeout): show the error/timeout
  reason, offer to retry (re-run the same step) or skip (config stays saved,
  user can retry later by restarting the service manually — the existing
  `journalctl`-based path is not removed, just no longer the *only* path).
- The spawned `listen()` task is **only aborted** on failure/timeout/skip.
  On success, it's left running for the remainder of the `brai onboard`
  process's lifetime (which then exits normally, ending the task) — this is
  a known, explained limitation: the live pairing session doesn't persist
  past the onboard CLI process, but the *paired device* does (stored in
  `session_path`'s SQLite file), so the subsequent service restart picks it
  up without re-pairing.

## Architecture

### 1. `PairingEvent` broadcast in `WhatsAppWebChannel`

New file location: `crates/zeroclaw-channels/src/whatsapp_web.rs` (existing
file, additive changes only).

```rust
#[cfg(feature = "whatsapp-web")]
#[derive(Debug, Clone)]
pub enum PairingEvent {
    Code(String),
    Connected,
    LoggedOut,
    StreamError(String),
}
```

New field on `WhatsAppWebChannel`:
```rust
pairing_events: Arc<parking_lot::Mutex<Option<tokio::sync::broadcast::Sender<PairingEvent>>>>,
```

New public method:
```rust
pub fn subscribe_pairing_events(&self) -> tokio::sync::broadcast::Receiver<PairingEvent> {
    let mut guard = self.pairing_events.lock();
    let sender = guard.get_or_insert_with(|| tokio::sync::broadcast::channel(8).0);
    sender.subscribe()
}
```

The channel is created lazily — only when something subscribes. `listen()`'s
existing event handlers (`Event::PairingCode`, `Event::Connected`,
`Event::LoggedOut`, `Event::StreamError`) each gain one additional line: if
`pairing_events` holds a sender, `let _ = tx.send(PairingEvent::X(...))`.
This is purely additive to the existing `eprintln!`/`tracing` calls at those
sites — production behavior (the real `brai` service, no one subscribed) is
unaffected; `send()` on a channel with zero receivers is a cheap no-op error
that's discarded.

### 2. Onboard wizard: unchanged

`crates/zeroclaw-runtime/src/onboard/mod.rs`'s `channels()` function and
`prompt_fields_under` are **not modified**. WhatsApp continues to be
configured exactly like every other channel via the existing generic,
schema-driven prompts.

### 3. `main.rs`: detect new WhatsApp config + run the pairing step

In `src/main.rs`, around the existing `match (*quick, *use_cli) { ... }`
block that calls `run_onboard(&mut cfg, &mut ui, target, &flags)` (four call
sites, one per UI backend):

1. Snapshot whether WhatsApp was configured *before* the call:
   `let wa_before = cfg.channels.whatsapp.clone();`
2. After `run_onboard(...)` returns successfully, compare:
   `cfg.channels.whatsapp` is `Some(wa_after)` and either `wa_before` was
   `None`, or `wa_before.pair_phone != wa_after.pair_phone` or
   `wa_before.session_path != wa_after.session_path`.
3. If changed, normalize `wa_after.master_identity` in place (strip
   non-digits, re-add a leading `+`; if the result is empty, warn and skip
   pairing — the operator can re-run onboarding to fix it) and persist that
   normalization back to `cfg` before calling the new pairing step.
4. Call `run_whatsapp_pairing_step(&wa_after, &mut ui).await` (new function,
   defined in a new file `src/whatsapp_onboard.rs` to keep `main.rs` from
   growing further — `main.rs` is already large and this is a
   self-contained unit).

This check-and-call happens identically after each of the four
`run_onboard` call sites (`QuickUi`, `TermUi`, `RatatuiUi`-success,
`RatatuiUi`-fallback-to-`TermUi`) since each constructs its own `ui` in a
different `match` arm; the pairing step reuses whichever `ui` value that arm
already has in scope, so the pairing prompts render through the same
backend the user is already looking at.

### 4. `run_whatsapp_pairing_step` — the pairing step itself

New file: `src/whatsapp_onboard.rs`.

```rust
pub async fn run_whatsapp_pairing_step(
    wa: &brai_config::schema::WhatsAppConfig,
    ui: &mut dyn brai_config::traits::OnboardUi,
) -> anyhow::Result<()>
```

Steps:
1. Construct a `WhatsAppWebChannel` from `wa`'s fields (same constructor
   call as `orchestrator/mod.rs`'s `build_channel_by_id`/
   `collect_configured_channels`, minus `.with_contact_gate(...)` — the
   pairing step doesn't need the gate, it's not receiving real traffic yet).
2. `let mut events = channel.subscribe_pairing_events();`
3. `let channel = Arc::new(channel); let handle = tokio::spawn({ let channel = channel.clone(); async move { let (tx, _rx) = tokio::sync::mpsc::channel(1); channel.listen(tx).await } });`
4. Loop, using `tokio::time::timeout(Duration::from_secs(60), events.recv())`:
   - `Ok(Ok(PairingEvent::Code(code)))` → `ui.note(&format!("WhatsApp pair code: {code}\n\nOn the dedicated WhatsApp number's phone: Settings → Linked Devices → Link a Device → Link with phone number instead → enter this code."))`; reset the timeout window (loop again) to wait for `Connected`.
   - `Ok(Ok(PairingEvent::Connected))` → `ui.status("WhatsApp connected successfully.")`; `ui.note("Restart the brai service now (e.g. `systemctl restart brai`) to start using WhatsApp.")`; `return Ok(())` (handle is intentionally left running, not aborted).
   - `Ok(Ok(PairingEvent::LoggedOut))` / `Ok(Ok(PairingEvent::StreamError(e)))` → `handle.abort()`; `ui.warn(&format!("WhatsApp pairing failed: {reason}"))`; go to step 5 (retry prompt).
   - `Err(_timeout)` → `handle.abort()`; `ui.warn("Pair code expired or no response received.")`; go to step 5.
5. Retry prompt: `if ui.confirm("Try WhatsApp pairing again?", true).await?` is `Answer::Value(true)`, restart from step 1; otherwise `ui.note("You can retry later by restarting the brai service manually.")` and return `Ok(())`.

### 5. Error handling

- If `WhatsAppWebChannel::new(...)` construction or `listen()`'s first
  `.await` errors immediately (e.g. malformed `session_path`), that surfaces
  as `Ok(Err(...))` from the spawned task — the step's loop won't see a
  `PairingEvent` at all and will hit the 60s timeout, which is an acceptable
  (if slightly slow) fallback; the timeout message covers this case too.
- The pairing step never causes `brai onboard` to exit non-zero — pairing
  failure is reported and offered a retry, but onboarding itself already
  succeeded (config is saved regardless).

## Testing

- Unit test for the `master_identity` normalization function (pure,
  extracted as a small free function in `src/whatsapp_onboard.rs`): strips
  `+`, spaces, dashes; rejects empty/non-digit input.
- `PairingEvent` broadcast: a `#[tokio::test]` in `whatsapp_web.rs` that
  subscribes, triggers each event path synthetically (reusing whatever
  minimal test scaffolding the existing `whatsapp_web.rs` tests use — no new
  mock framework), and asserts the expected `PairingEvent` variant arrives.
- Manual end-to-end verification against a real WhatsApp Web pairing
  (already a requirement from the earlier contact-gate work) — this is a
  live external protocol integration; automated tests cover the broadcast
  plumbing and normalization logic, not the actual WhatsApp handshake.

## Non-goals (explicitly deferred)

- No automatic `systemctl restart` or equivalent — manual instruction only.
- No changes to the generic onboard wizard's channel-picker flow.
- No pairing-step support for any other channel (this is WhatsApp-specific,
  triggered only by WhatsApp config changes).
- No persistence of the pairing-step's `listen()` task beyond the `brai
  onboard` process's own lifetime.
